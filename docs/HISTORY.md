## 保存方式（予約ファイル方式 → 一時ファイル + os.rename）

- 日付: 2026-10
- 以前の考え: ``output_path`` が指す本番の名前の空ファイルを ``open("x")``
  で予約し、CSV を書いた一時ファイルを ``os.replace`` で中身だけ置き換える
  2 段構え。これにより「途中でクラッシュしても空の本番ファイルは残る」
  状態を避け、 ``CSV()`` 側の ``atomic_write`` で書き終わったら原子的に入れ替える。
- いまの考え: 本番の名前の空ファイルを **一瞬も作らない** 保存方式に統一。
  ``paths.move_into_place()`` ヘルパーで ``~`` プレフィックスの一時ファイル
  に全部書いてから ``os.rename``（Windows では既存があると
  ``FileExistsError``）で最終パスへ移し、既存があれば連番 ``_1`` / ``_2`` … で
  別名を確保する。上書きモードだけ ``os.replace`` で毎回上書きする。
- 理由: 会社のファイルサーバー（UNC）で「ログ上は 243493 行で成功、ファイル
  が 0 バイト」事案が発生（後日、保存先のクォータ不足と判明）。予約ファイル
  方式は書き込み中ずっと本番の名前で空ファイルが見えてしまう作りでもあり、
  これを機に空ファイル自体を作らない方式に置き換えた。0バイト検出は
  [`SavedFileEmptyError`](#0バイト保存の検出-savedfileemptyerror) で担保。

## 0バイト保存の検出 `SavedFileEmptyError`

- 日付: 2026-10
- 以前の考え: なし（事案発生後に追加）。
- いまの考え: 保存直後に ``Path.stat()`` で 0 バイトを検出したら
  ``SavedFileEmptyError`` で例外を上げる。``DownloaderError`` 系なので
  ``_failure_row()`` 側で「Salesforce」区分に分類され、プログラム扱いには
  しない。
- 理由: ファイルサーバーへの書き込みは手元でバッファしてから送られるため、
  クォータ不足で中身が捨てられても Python 側ではエラーにならない。空の
  ファイルを成功扱いにしないため、書き込み直後に必ずサイズを確認する。
  根拠となった事案の詳細は [保存方式](#保存方式予約ファイル方式--一時ファイル--osrename) を参照。

## 出力パスの組み立て 1 本化

- 日付: 2026-09
- 以前の考え: フォルダは「ベースパス / 担当者 / 概要 / ファイル」の 3 階層
  と、別パターン（ファイル名に時刻を混ぜる／混ぜない）が混在していた。
- いまの考え: ``ベースパス / 概要 / {管理番号}_{YYYYMMDD}_{HHMM}.csv``
  （上書きモード時は ``{HHMM}`` のみ）に統一。``src.paths.output_path()``
  が唯一の組み立て元。
- 理由: 組み立てロジックを 1 か所にまとめることで、管理表の列から出力
  パスを予測できるようにし、過去のパターン差異に起因する混乱をなくす。

## 出力パスから `担当者` / `概要` を除外

- 日付: 2026-09
- 以前の考え: 出力パスのフォルダ名やファイル名に `担当者` や `概要` を
  含めていた。
- いまの考え: `担当者` は記録用に管理表に残すが **出力パスには使わない**。
  `概要` はフォルダ階層の 1 段目にだけ使う（人が業務ごとに探しやすくする
  ためで、ファイル名には混ぜない）。
- 理由: フォルダ階層は「グループ単位」が主軸（同じグループのレポートが
  複数フォルダに散らばると運用上困る）。`担当者` は異動で変わると過去
  ファイルと整合しなくなるため、パスの一部にしないほうが安全。

## 自動切替導入と「当日失敗時のスキップ」廃止

- 日付: 2026-10
- 以前の考え: 当日中に ``SalesforceReportTruncatedError`` で失敗した
  レポートは当日中は再問い合わせしない（同じ失敗を何度も繰り返さない）、
  というスキップを ``scheduler.py`` に入れていた。
- いまの考え: Report API が 2000 件超で打ち止められたら自動でブラウザ経由
  に切り替えて取り直す自動切替を入れたため、**当日中の再問い合わせでも
  自動切替が効く**。スキップは不要になり、 ``already_failed`` は常に空
  リストを返す。
- 理由: Report API → ブラウザ自動切替は初回と同じ動作をするので、当日中に
  何度走らせても Salesforce への問い合わせ動作は変わらない。「失敗を
  覚えて再試行をスキップする」状態は、ちまたの状況（ブラウザ経由は
  状況依存）でも整合性が崩れやすいので廃止した。
- → 新しい判断は [ブラウザ経由を別リポジトリに分ける](#ブラウザ経由を別リポジトリに分ける)（2026-11-12）を参照

## SOQL 件数比較

- 日付: 2026-10
- 以前の考え: ``SoqlReport.bulk_query()`` の結果をそのまま保存していた。
- いまの考え: ``SoqlReport.CHECK_COUNT = True``（既定）のとき、
  ``bulk_query()`` の **直後** に **同じ接続のうち** にもう 1 度 Report API
  を叩いて ``factMap["T!T"]["aggregates"]`` の ``RowCount`` を取り、
  ``len(table)`` と比べる。一致すれば INFO ログ 1 行出して返す。一致
  しなければ ``SoqlCountMismatchError`` で **保存させずに** 例外を上げる
  （一時ファイルも作らない）。
- 理由: 大量データを ``bulk_query()`` で取る系で、サーバー側の集計が
  途中で打ち切られていても気付かない事故を防ぐ。``site_for()`` を
  増やさず 1 回のログイン内で完結させるため、「同じ接続のうち」に
  もう 1 度 Report API を叩く。

## SOQL 未完成の検知

- 日付: 2026-10
- 以前の考え: なし。
- いまの考え: ``SoqlReport.soql()`` が返した本文の先頭（前後の空白を除く）
  が ``INCOMPLETE_SOQL_MARKER`` で始まる SOQL は ``bulk_query()`` を呼ぶ
  **前**に ``SoqlIncompleteError`` で止める（Salesforce には問い合わせない）。
  印の文字列は ``soql.INCOMPLETE_SOQL_MARKER`` の定数で soql-collector 側の
  ``INCOMPLETE_MARKER`` と同じ。
- 理由: 下書き中の SOQL をうっかり保存先に流して「0 件が常に返る」状態に
  なるのを防ぐため、印のあるものは Salesforce に問い合わせる前に止める。

## SOQL 加工 transform() の呼び出し位置

- 日付: 2026-10
- 以前の考え: ``bulk_query()`` の直後に ``transform()`` を呼んでいた
  （=加工後の件数で比較していた）。
- いまの考え: 件数比較の **あと** に ``SoqlReport.transform()`` を **加工前
  の生の結果**に対して呼ぶ。加工後が 0 行のときは既存の ``ALLOW_EMPTY``
  判定がそのまま動く。
- 理由: 件数比較は加工前の件数で行うべき（レポートの総件数と比べるのが
  妥当）。``transform()`` は保存直前の整形なので順序を分けた。

## `列名の対応.csv` の統合（全体で 1 ファイル）

- 日付: 2026-10
- 以前の考え: レポートは ``SoqlReport.COLUMN_NAMES`` を個別に手書きして
  表示名を決めていた。
- いまの考え: soql-collector が出力する ``<ベースパス>/soql-collector/列名の対応.csv``
  を **全体で 1 ファイル**に統一。形式は
  ``主オブジェクト, SOQL列名, 表示名, 備考, 更新日``。
  ``(主オブジェクト, SOQL列名)`` が同じならどのレポートでも同じ
  表示名が引かれる。``SoqlReport.COLUMN_NAMES`` の **手書きは優先**
  （同じキーは手書きが勝つ）—「直したい列だけ書けばよい」を崩さないため。
- 理由: 同じ ``Account.Name`` を 10 レポートで重複手書きする状態を避け、
  列名の変更を 1 か所で反映できるようにする。``SOQL`` 列を ○ にした
  レポートが ``SoqlReport`` 経由なら、手書きが無くても soql-collector
  を 1 度走らせるだけで列名が出る。

## `schedule_key` 引数の既定値

- 日付: 2026-10
- 以前の考え: （議論メモ） ``schedule_key`` を必須化すると、
  旧 API で ``schedule_key`` を渡さずに失敗情報を書いていた呼び出し側が
  壊れる、という懸念があった。
- いまの考え: ``record_success()`` / ``record_failure()`` の ``schedule_key``
  引数は **既定値 = 空文字** とし、引数を省略しても動く。dedup 判定は
  成功行しか見ないので、履歴追跡用（失敗時のスケジュール行を後から追える
  ように）の引数に過ぎない。
- 理由: 後方互換のためではなく、**「失敗履歴にどのスケジュール行かを残すか」
  が分かっているときだけ書く** というのを表現するため。省略できる方が
  呼び出し側が意図を表現しやすい。

## `report_folder()` の組み立てルール = ベースパスのみ

## `_` は「そのファイルの中だけで使う」印にそろえた

- 以前の状態: `service.py` を `service/` に分けたとき、別ファイルから使う関数（`_fetch_via_api` /
  `_save` / `_select_targets` など 11 個）に `_` が付いたまま残り、別ファイルから `_` 付きの名前を
  import していた。
- いまの決まり: `_` は定義したファイルの中だけで使う印。別ファイルから使う内部の関数には付けない
  （comken の `docs/CONVENTIONS_PYTHON.md` の命名規則と同じ）。
- `_save` は `save_report` にした。モジュール名が `save.py` で、openpyxl の `.save()` とも紛らわしく、
  `save` のままだと `save.save` になるため。
- `tests/test_private_naming.py` が、別ファイルからの `_` 付きの使用を検出する。

## SOQL 取り方の切り替え（`USE_BULK`）

- 日付: 2026-11
- 以前の考え: ``SoqlReport`` の SOQL は必ず ``bulk_query()``（Bulk API 2.0）で
  取っていた。集計関数や ``GROUP BY`` を使う SOQL は作れなかった。
- いまの考え: ``SoqlReport.USE_BULK``（既定 ``True`` = ``bulk_query()``）で
  レポートごとに選べる。 ``False`` にすると REST の ``query()``（ページ送り）で
  取り、 集計関数・``GROUP BY`` も使える。 INFO ログには ``取得方法=Bulk`` /
  ``取得方法=REST`` が出る。
- 理由: Bulk API 2.0 は件数が多い取得では速いが、 受け付けない SOQL 構文がある。
  取り方を切り替えられるようにし、 集計レポートも SOQL 化できるようにする。
  値の形（文字列か数値か）と 0 件時の列の有無は経路で変わるため、
  ``USE_BULK=False`` のときの注意は ``SoqlReport`` の docstring に明記した。

## 「不明」を書けるようにする（管理表の「0件あり」「2000件超」）

- 日付: 2026-11
- 以前の考え: bool 列の `choices` は「○」「×」の2つだけで、「○」「×」以外の文字を
  書くと `MasterRowValueError` になる。「0件あり」「2000件超」も同じ。
- いまの考え: **「0件あり」「2000件超」の2列だけ** `choices` に「不明」を加える。
  「不明」は **空欄と同じ扱い**（False）で読む。読み込み側の変換
  （`src.report_master._convert_bool`）で「不明」→ False を **明示** する
  ——comken の `is_enabled_mark` の語集合に無いため偶然 False になるのを
  待たない。雛形のドロップダウンと「記入方法」シートにも「不明」が出る。
- 理由: 本番の件数が分からないとき、`×` は「0 件にはならない」「2000 行超えではない」
  と断定してしまう。**断定を避けるためだけの表記**で、**挙動は `×` と同じ**にする
  （0 件は `EmptyReportError`、Report API 経路のまま）。そうすれば自動切替
  （Report API で上限超え→ブラウザ、0 行→ブラウザで取り直し、それでも 0 行ならエラー）は
  そのまま働く。「不明」を許すのは2列だけにして、他の bool 列は「○」「×」のままにする
  （表記を1つに絞って読み方の揺れを防ぐため）。
- → 自動切替は 2026-11-12 に廃止した。新しい判断は
  [ブラウザ経由を別リポジトリに分ける](#ブラウザ経由を別リポジトリに分ける)を参照
  （「不明」の扱い自体は変えない）

## 管理表に「RPA使用」「集計形式」を足す

- 日付: 2026-11
- 以前の考え: 管理表の列は取得経路（`0件あり` / `2000件超` / `SOQL`）と保存方式
  （`上書き`）を表すものだけで、「RPA でもこのレポートを取るか」「レポートの
  形式が何か」はどこにも記録していなかった。別のプロジェクト（RPA、
  soql-collector）が同じ管理表を各自の判断で読んでいた。
- いまの考え: `ReportEntry` に **`uses_rpa`（RPA使用・bool）** と
  **`report_format`（集計形式・str）** を足す。どちらも**記録用**で、
  取得経路・保存・履歴の動きは変えない。値は定数
  （`REPORT_FORMAT_SUMMARY` / `REPORT_FORMAT_MATRIX` / `REPORT_FORMAT_NONE`）で
  1か所に持つ。列は「SOQL」の直後（=取得経路に関わる列の近く）に置き、
  既定値（`×` / `無し`）を持つので**列が無い既存の管理表もそのまま読める**。
- 理由: 同じ管理表を複数のプロジェクト（このダウンローダー / RPA /
  soql-collector）が読むため、**共有できる情報は管理表の列に置く**のがいちばん
  安い。列を足しても既存管理表が止まらないよう既定値を必ず持たせ、記録用である
  ことを `help` に明記して、取得経路の列と混同しないようにする。「集計形式」の
  値（`サマリー` / `マトリックス` / `無し`）は soql-collector も同じ文字列で
  読むので、**表記を変えない**（定数化して1か所にする）。

## 列名の置き換えを `transform()` より前にする

- 日付: 2026-11-12
- 以前の考え: 列名の置き換え（``COLUMN_NAMES`` / ``列名の対応.csv``）は
  保存直前の ``save_report()`` で行っていた。 そのため ``transform()`` は
  SOQL の API 名（``Name`` / ``Amount``）を受け取る形だった。
- いまの考え: 列名の置き換えを **取得側**（``fetch_via_soql()``）に置き、
  件数の比較のあと・``transform()`` の **前** に行う。 ``transform()`` は
  **表示名の列** を受け取る。 ``save_report()`` は列名の置き換えをしない
  （受け取った ``Table`` をそのまま CSV に書く）。
- 理由: ``transform()`` を表示名で書けるようにするため。 ``transform()`` は
  人が書く Python で、 表示名（＝出力 CSV の見出しと同じ名前）で書いた方が
  出力と読み合う。 順番は試験用リポジトリ（``soql-report-tester``）と揃えた。

## ブラウザ経由を別リポジトリに分ける

- 日付: 2026-11-12
- 以前の考え: ブラウザ経由の取得（``src/service/browser.py``）を本体に置き、
  管理表の「2000件超」が ○ の行は自動でブラウザ経由に切り替えて取り、
  Report API が 2000 件超で打ち切られたとき・0 件のときは自動でブラウザに
  取り直していた。
- いまの考え: **ブラウザ経由は別リポジトリ ``salesforce-report-browser``
  に分ける**（このリポジトリの外）。本体はブラウザを操作せず、
  ``download_scheduled(fetch_browser=...)`` の引数で「1 件取りに行く関数」を
  外から受け取る。関数が渡された実行では **対象選定で選ばれた、当日まだ
  取れていない行を全部** 対象にする（経路が SOQL でも通常でも問わない。
  **本体の後に実行する前提**）。渡されない実行（本体の通常実行）では
  管理表の「2000件超」が ○ の行を **取らない**
  （1 実行 1 行の INFO ログを出して外す。履歴にも書かない）。
  **自動の取り直しはやめた** ── Report API が 2000 件で打ち切られたときは
  ``SalesforceReportTruncatedError`` のまま失敗にし、0 件で「0件あり」が × の
  ときは ``EmptyReportError`` のまま失敗にする。対処は管理表の「SOQL」か
  「2000件超」を ○ にすること（ログに 1 行出る）。
  管理表・保存先・履歴は分けないので、別リポジトリは **本体を import して
  ``fetch_browser`` を渡す**。保存（``save_report``）・履歴（取得経路は
  ``ROUTE_BROWSER``）・失敗の分類・排他（``HistoryFileLock``）・対象選定
  （スケジュール・当日成功済みの判定）は本体側の処理をそのまま通す。
- 理由: ブラウザ経由は **MFA を人が承認する** 前提で、無人の定期実行とは
  性質が違う。無人の実行に人が承認するステップを埋め込むと、止まったときに
  原因が分からず、誰が何を待っているかが履歴にも残らない。ブラウザの
  起動・ログイン・使い回しはブラウザ側の責務として切り離し、本体は
  「取得経路を選ぶ・保存する・履歴に残す」だけに保つ。分けた後も管理表と
  履歴は 1 つにしたいので、別リポジトリから本体を import して
  ``fetch_browser`` を渡す形にした（管理表・保存先・履歴が二重にならない）。
  自動の取り直しをやめたのは、打ち切り・0 件は **失敗として見せる** ほうが
  原因に気づけるからで、SOQL 化か「2000件超」を ○ にして直す運用に変えた。
  ブラウザ側は本体の取り残しを全部拾う役。自動の取り直しを本体から外しても、
  取れなかったレポートを同じ日のうちに取れる。

## SOQL レポートを置く場所を `src/reports/` に移す

- 日付: 2026-11-12
- 以前の考え: SOQL レポート（2000件超のレポートを SOQL で取るもの）の置き場所は
  ``src/soql_reports/`` 配下の ``reports/`` ディレクトリ、 基底クラス
  ``SoqlReport`` は ``src/soql_reports/`` 配下の ``base.py`` に置いていた。
  レポートの import は ``src.soql_reports`` 配下の ``base.py`` から
  ``SoqlReport`` を取る形だった。
- いまの考え: レポートの置き場所を **``src/reports/``** に移す。 基底クラス
  ``SoqlReport`` も **``src/reports/base.py``** に移し、 レポートの import は
  ``from src.reports.base import SoqlReport`` になる。 ``src/soql_reports/`` には
  ``_registry.py`` / ``__init__.py`` / ``column_names.py`` / ``runner.py`` を残す
  （登録の走査は ``src/reports/`` を見る）。 移行の互換（古い import 先を残す
  別名・shim）は作らない。 soql-collector（別リポジトリ）が生成する .py の
  import も ``from src.reports.base import SoqlReport`` に直す。
- 理由: レポートを置く場所を浅くして分かりやすくするため（ユーザー判断）。
  基底クラスもレポートと同じ場所に置き、 生成した .py の import 先と
  置き場所を一致させた。

## dry-run で履歴に残さない

- 日付: 2026-11-14
- 以前の考え: dry-run ではファイルを作らないが、履歴には成否を書いていた。
- いまの考え: ``src.history.record()`` が ``comken.runtime.is_dry_run()`` を
  見て、成功でも失敗でも **履歴に書かない**（INFO ログを 1 行出して終わる）。
- 理由: 履歴に「成功」が残ると、同じ日の本番の取得が「当日取得済」で飛んで
  しまうため。dry-run は本番の判定に一切影響させない。
